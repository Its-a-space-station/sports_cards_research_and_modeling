# Spike: GemRate population data (2026-09-15)

**Verdict: FEASIBLE.** Universal search works headless and returns structured
JSON; card pages sit behind a Cloudflare challenge that resolves headless with
one ~10 s wait. Collector implemented in `src/cardprice/pop_gemrate.py` with
offline parser tests (`tests/test_pop_gemrate.py`, fixtures under
`tests/fixtures/gemrate/`).

Evidence: verbatim response excerpts below; committed fixtures
`tests/fixtures/gemrate/search_henderson.json` (10 search results) and
`tests/fixtures/gemrate/card_details_henderson.json` (full `/card-details`
payload for the Henderson base card), both captured 2026-09-15 via Playwright
headless (`PLAYWRIGHT_BROWSERS_PATH=.pw-browsers`, UA = `web.USER_AGENT`).

## (a) Universal search: type → debounced POST → JSON results

- `https://www.gemrate.com/universal-search` loads headless **unchallenged**
  (title `Universal Search - Pop Report Data for PSA, Beckett, SGC, CGC | GemRate`).
- Search input is `#search` (placeholder
  `Try "1986 Fleer Michael Jordan #57" or "Pikachu Grey Felt Hat"`). The widget
  (`/static/dist/universal-search-widget.js`) debounces keystrokes, then fires:

  ```
  POST https://www.gemrate.com/universal-search-query
  {"query":"Gunnar Henderson 2023 Topps Chrome #2","page":1}
  ```

  Response (200, JSON) has `results[]` with **structured** fields — no DOM
  scraping needed. Verbatim first two results trimmed:

  ```json
  {
   "description": "2023 Topps Chrome Gunnar Henderson Base 2",
   "gem_rate": 0.624427,
   "gem_total": 2996,
   "gemrate_id": "7fbc276ca4b0956fbfd703bcc2cb2b29b63b432a",
   "graders_included": ["psa", "beckett", "sgc", "cgc"],
   "is_universal_match": true,
   "parsed_description": {"card_number": "2", "category": "baseball-cards",
     "name": "Gunnar Henderson", "parallel": "Base", "set_name": "Topps Chrome",
     "subset": null, "year": "2023"},
   "total_population": 4798
  }
  ```

  Result 2 is the same card as `parallel: "Refractor"` — parallels are separate
  entries, so picking the **base** card = `parsed_description.parallel == "Base"`
  plus exact `year` / `name` / `card_number` / `set_name` match
  (`pick_search_result`; set-name falls back to token-subset).
- Results render in the DOM as anchors `/card/<gemrate_id>`, but the JSON is the
  robust path. Pagination: `has_more`/`page`; page 1 comes from typing into
  `#search`, pages 2+ via in-page `fetch` of the same endpoint (only fetched
  when page 1 yields no match, 5 s apart).
- Flakiness observed: on one run the POST did not fire within 12 s of typing
  (and `/search-presets` answered 403 — Cloudflare rate limiting). The collector
  re-types the query once before giving up (`_search_results`); the retry
  succeeded in the live test.

### Matching rules discovered on the 13-card run

- **SP-only cards**: 2022 Topps Chrome #221 (Witt) and #222 (Rodriguez) have
  **no `Base` entry** on GemRate — they exist as `parallel: "SP"` (short print;
  PSA numbers the SP as the base card). `pick_search_result` falls back to
  `parallel == "SP"` when no Base candidate matches (all other fields exact).
  Their pops below are the SP entries (540 / 553).
- **USC-prefix drift**: SCP slugs keep the `USC` card-number prefix
  (`nick-kurtz-usc178`); GemRate's true base entry for 2025 Chrome Update drops
  it (`Nick Kurtz Base 178`) while exact-`USC178` entries are all refractor-line
  variants. The matcher ranks *digits-only number match in the exact set* above
  *exact number match in a lookalike set* — this flipped Kurtz from a wrong
  5-pop "Topps Chrome Update Refractors" entry to the true 629-pop base card.
- Every matched description was audited against the seed list (see table);
  2024 Chrome Update uses proper `USC` numbering on GemRate (`Base USC88`),
  so Skenes needed no digit fallback.

## (b) Card page: Cloudflare challenge, then `/card-details` JSON

- `/card/<gemrate_id>` 301-redirects to `/card/<gemrate_id>/<slug>`, e.g.
  `/card/7fbc.../2023-gunnar-henderson-topps-chrome-2`.
- The card page **is** challenged ("Just a moment..."). With a 6 s wait it stayed
  challenged; with 10 s waits it resolved on the first retry cycle in every
  successful run (same retry pattern as `web.fetch_page`: 3 × 10 s, then
  `ChallengeError`).
- Once through, an inline script mints `cardDetailsToken` and fetches:

  ```
  GET /card-details?gemrate_id=<id>
  X-Card-Details-Token: <token from page>
  ```

  The collector captures this response passively (`page.on("response")`) rather
  than re-calling the API — the token is per-page-load and not worth replaying.
- Payload (fixture) gives everything the panel needs:

  ```
  total_population = 4798
  total_gems_or_greater = 2996          -> gem_rate = 2996/4798 = 0.6244 (page: 62.4%)
  population_data[grader=="psa"]: card_total_grades = 3129, grades.psa_10 = 2070,
                                  card_gem_rate = 0.661553
  data_last_updated = 2026-09-14, last_population_change = 2026-08-25
  ```

- Rendered-DOM cross-check (also in the fixture run): `#stat-pop-value` = 4,798,
  `#stat-gem-value` = 62.4%, and `table#gradesTable` verbatim PSA row:

  ```
  POP  GEMS+  GEM RATE  PERFECT PRISTINE GEM MINT MINT+  9    8    7  6 5 4 3 2 1 A
  PSA  3,129 2,070  66.2%                      2,070      -  896  129  18 9 2 0 0 0 0 5
  ```

  i.e. "GEM MINT" for PSA = PSA 10 = `grades.psa_10` = 2,070. JSON ↔ DOM agree.

## (c) Pop growth over time: exists, but on a separate form-driven page

- The card page itself shows **no time series** (its `#population-chart` canvas
  is the grade-distribution sparkline with All/PSA/BGS/SGC/CGC tabs).
- Weekly pop history lives at `https://www.gemrate.com/population-trend`
  (Insights → Grading Trends → Card): an ag-grid table
  `Date | Total Gems | Total Grades | Gem Rate` with weekly rows (observed 53
  rows back to 2025-09 for a 2025 football card) plus an Export-to-CSV button.
  **But** it is form-driven — grader tab (PSA/Beckett/SGC only), sport category,
  and `year`/`set_name`/`name`/`parallel`/`card_number` fields with a csrf-token
  POST — one grader per view. Driving it for 13 cards is a second, more brittle
  interaction and is **not collected** in this pass. The panel gets
  pop-growth-over-time from our own dated monthly snapshots
  (`pop_snapshots.csv` appended monthly), which is what the brief's interface
  specifies.

## (d) Collector mechanics, cost, politeness

- `fetch_pop(query, match={name, year, set_name, card_number}, page=None)` →
  `{psa_10_pop, psa_total_pop, total_pop, gem_rate, description, gemrate_id,
  data_last_updated, query, gemrate_url}`. `collect_pops(cards_seed)` builds the
  query from the SCP URL (`build_query`: "Gunnar Henderson 2023 Topps Chrome #2";
  card number = last slug token, so `paul-skenes-usc88` → `#USC88`) and appends
  `date, card_slug, psa_10_pop, total_pop, gem_rate` rows to
  `data/reference/pop_snapshots.csv` (same-day reruns idempotent). Full parsed
  payloads also snapshot to `data/raw/pop_gemrate/<slug>/<date>.json` (gitignored).
- One shared headless Chromium session per run keeps Cloudflare clearance across
  cards. Timing per card: search load 5 s + type/poll ~3 s + card page 10 s +
  capture poll ~1 s + inter-card sleep 6 s ≈ **25–30 s/card**; 13 cards ≈ 6–7 min.
  Every gap between gemrate.com interactions is ≥5 s.
- Failure handling: unresolved challenge → `ChallengeError`; empty/no-match
  search or missing JSON → `PopLookupError`; Playwright errors caught per card —
  the row is written with empty pop fields and the run continues.

## (f) Notes for Plan 4

- `pop_snapshots.csv` joins to the panel on `card_slug` (same
  `<set-slug>/<player>-<number>` convention as `collect_prices.card_slug`).
- `gem_rate` is all-graders combined (GemRate's headline number);
  `psa_10_pop` is PSA-specific. A card with no PSA row would get
  `psa_10_pop = NULL` — none after the matching fixes above; the collector
  handles it (`parse_card_details` returns `None`).
- Witt #221 / Rodriguez #222 pops are GemRate **SP** entries, and Kurtz's came
  via the `USC178`→`178` digit fallback — treat those three rows' pop figures
  as slightly softer than the others (documented in the table).
- Re-run monthly: `python -m cardprice.pop_gemrate` appends a new `date` row per
  card (run from repo root with the venv active and
  `PLAYWRIGHT_BROWSERS_PATH=.pw-browsers`).
